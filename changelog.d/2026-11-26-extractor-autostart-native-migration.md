### Fixed (2026-11-26 — an update names the one command that moves a Python extractor autostart to the native shim)
- A machine installed with the Python client and the `claude-only`, `claude-fallback`, `openai-only` or `openai-fallback` extractor mode has an extractor shim autostart that runs `ops/shim_autostart.py run claude|codex` under Python: a systemd user unit on Linux, a scheduled task on Windows. When `pseudolife-mcp update` moves such a machine to the native client, that autostart keeps running Python. The client step reported it only in a checkout update with `-All`, and said only "rerun native extractor setup"; a release update did not look at it at all.
- Every update now reports it in its `autostart` row (a release update shows the row only when it finds a registration) and names the exact command that moves it: `pseudolife-mcp extractor-shim install-autostart <kind> --repo <checkout> --native-exe <stable launcher>`, plus the log path the settings name (made absolute against the checkout). That native setup stops the Python shim, registers the native one under the same name with the settings the Python runner read from `<checkout>/ops/.env`, checks that it serves and puts the Python registration back when it does not. When the stable launcher is not yet the native client's, the row says to run `pseudolife-mcp update --clients-only` first.
- The update itself changes no autostart: an update without a person never changes the engine, a handed-off update cannot tell whether a person started it, and the move can have effects nobody chose (it enables a unit that was disabled and replaces the pre-rename Sonnet task).
- The runner is recognised exactly, from the unit's single `ExecStart=` line or the task's encoded start info (a Python interpreter running `<checkout>/ops/shim_autostart.py run <kind>`). Other Python-era forms keep the general note, and a native registration whose description mentions the runner is no longer reported as stale. macOS has no extractor autostart.
