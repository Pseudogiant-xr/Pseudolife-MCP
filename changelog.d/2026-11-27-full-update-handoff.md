### Changed (2026-11-27 — one `pseudolife-mcp update` applies the new release's own update rules)
- A release-mode `pseudolife-mcp update` on a Docker host used to make its engine and daemon decisions with the client already installed, so a release that changed how the daemon is updated took effect only on the second update. Now, when the target release is newer than the running updater, the update first downloads that release's client, checks it against the release's `SHA256SUMS`, and lets it run the whole update, daemon step included, with the same arguments: plain, `--daemon-only` and `--unattended` runs alike. The newer updater asks any question an attended run asks, installs itself as the shim runtime in its own client step, and its exit code, `--json` report and `--result-file` are the run's. If its client cannot be downloaded, checked or started, the run says so in one line and finishes on its own code. There is no hand-off to the running release, on a downgrade, for `--clients-only` (which keeps the client-step hand-off), for a checkout deploy, on a client-only machine, or for an unattended run whose daemon already runs the target or has `updates.unattended_daemon` off. Updaters older than 0.26.0 have no such hand-off: on those hosts, `pseudolife-mcp update --clients-only && pseudolife-mcp update` moves the client first, and the second command then does the whole move in one run.
