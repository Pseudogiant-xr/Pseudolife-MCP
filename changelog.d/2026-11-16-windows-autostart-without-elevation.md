### Fixed (2026-11-16 — Windows autostart and the daily update task no longer ask for an elevated PowerShell)
- The Windows extractor shim autostart (`ops\install-shim-autostart.ps1`, `ops\install-codex-shim-autostart.ps1`, the native `pseudolife-mcp extractor-shim install-autostart`) and the daemon autostart (`ops\install-autostart.ps1`) now register a task for the installing user only: a logon trigger for that user, run as that user with a limited token (`-LogonType Interactive -RunLevel Limited`). Windows lets an unelevated user register, replace and remove that kind of task, so the installers, `install-autostart --help`, `update --schedule`, `docs/guide/dreaming.md` and `docs/guide/configuration.md` no longer tell you to open an elevated PowerShell. The Python-era scripts used to register a trigger for any user's logon, and that is what needed elevation. Checked unelevated on a real desktop for the logon task, and with a UAC-style filtered token on the Windows dev VM for the logon and daily tasks.
- A task registered earlier from an elevated PowerShell is owned by Administrators, and a normal window can neither replace nor remove it. Every rerun now reads the task's owner first and changes nothing it cannot finish:
  - If the task is enabled, starts at this user's logon and already runs the same action (whatever release registered it), which reads its settings file at every start (`ops\.env` for the Python-era runner, the native shim's settings file), the rerun writes the new settings, leaves the task registered and restarts the shim at once, then checks that it serves. The Python-era scripts restart it themselves, stopping only the shim the runner recorded in its PID file (checked by start time and command line), never one found by a command-line pattern; the native client restarts it through Task Scheduler, which lets an unelevated user stop and start such a task (measured on the Windows dev VM). If the native restart fails, the shim it started is stopped, the old settings are put back, and the original is restarted on them if it was running; if the Python-era restart fails, the script says so and the new settings take effect at the next logon. One line says what happened.
  - In every other case the rerun refuses before writing or stopping anything. That covers an older task that carries its model and port on its own command line, the legacy `Pseudolife Sonnet Shim`, the other mode's shim task (the installer leaves it, says so, and finishes), a new `--schedule` time, and `--unschedule`. The refusal is one line that says why (for example "is disabled" or "runs an older command"), that the new settings were not applied, and ends with the one command to run once in a PowerShell opened with Run as administrator: `Stop-ScheduledTask` and `Unregister-ScheduledTask` for that task, after which a normal window is enough. The installers print only that line, and the native client exits 3 for it. A task owner that cannot be read is a refusal too, never a reason to go ahead.
  - A task of the same name that belongs to another account is never touched, not even from an elevated shell: one another user owns, or one Administrators own that runs as another account.
- The frozen Python client's own `pseudolife-mcp update --schedule` (`pseudolife_memory/unattended_update.py`) is unchanged, and its refusal text still names elevation, until that client is retired.
