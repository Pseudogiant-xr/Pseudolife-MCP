### Security (2026-11-16 — the native client checks that the daemon account can use its volumes, and repairs old root-owned files once, after a backup)
- `pseudolife-mcp update` (release and checkout modes), `backup`, `restore`, `move` (through the target's restore) and the native installers' reruns now first check, with a short helper container that runs as the daemon account (uid 10001) with no capabilities, no network and a read-only root filesystem, that this account can read every file and enter and write every directory in the daemon's state and model volumes. The check reads metadata only and writes nothing. A healthy host runs only this check: no root container is started for it.
- Where an older release left files that root owns, the client repairs them once: a helper running as uid 0 with only the CHOWN and DAC_READ_SEARCH capabilities, no network and a read-only root filesystem gives each uid-0 entry to 10001:10001. It follows no link, enters no other mount, changes owners only, and writes every path it changed, with the group it had, to a private log under `~/.pseudolife-mcp/ownership-repair/`; the user sees one line naming that log. The check then runs again, and an entry it still cannot use (another owner's, or on a filesystem that cannot change owners) is refused with its path and the one fix, with nothing else changed.
- The order protects the backed-up state: the model cache (outside backups) is repaired first; the state volume is repaired only after a verified archive of it exists (update archives it through the running old container, backup after its own pair, restore after its safety pair). `update --no-backup` on such a host refuses and asks for a run with the backup.
- The image entrypoint's own start-time transfer of root-owned state no longer walks into another volume mounted below `/data` or `/models`: two named volumes on one host filesystem share a device number, so `find -xdev` alone entered them.
