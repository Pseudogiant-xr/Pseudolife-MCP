### Changed (2026-11-14 — `connect` asks on a terminal and re-creates a stale unattended-update schedule)
- `pseudolife-mcp connect` without `--yes` on a terminal now asks "Apply these changes? [y/N]" natively, after the plan and before any authenticated request; anything but `y` or `yes` changes nothing. `--read-code` and `--read-token` read the pairing code and the token on a terminal without echo, as before. A run with no terminal and no `--yes` still refuses without changing anything, so unattended runs never wait.
- An unattended-update schedule that `pseudolife-mcp update --schedule` installed on this machine names its daemon URL, so moving the machine used to leave it running against the old daemon. With every client selected, `connect` now re-creates it for the new URL through `update --schedule` itself, keeping its daily time and kind, as a change row under the same confirmation. This covers the client machine's schedule ("Pseudolife Client Update" / `pseudolife-client-update`), which `connect` did not report before, as well as the daemon's.
- `connect` never creates a schedule and never removes one. A schedule whose command is not what `--schedule` writes, whose time cannot be read, or of a kind `--schedule` would not write on this machine is a manual row naming the command to run. So is the daemon's own schedule once the daemon has moved to another machine. If the re-creation fails after the registrations were re-pointed, the run says what changed and prints the one command that finishes it.
