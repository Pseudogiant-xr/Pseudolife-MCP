### Fixed (2026-11-03 — A full suite waits for another holder of its board lease)
- A full test suite that held its local lock started even while the board showed its lease (`full-suite`) held by someone else, printing only that it "carries on". A WSL suite cannot see a Windows-side `pseudolife-mcp lease run full-suite` lock, so a native build and a WSL suite ran on the same machine at once. Once a full run holds its local lock it now waits, in the board's queue order, until the board grants it the lease, naming the holder and its purpose about once a minute; `PSEUDOLIFE_SUITE_LOCK=fail` exits instead. The board decides when a hold has lapsed. A record under the run's own lock-directory label while no `lease hold` of the lease runs here, or the enclosing `lease run full-suite -- ...` the run was started by does not stop it: `lease run` now also records its pid in `PSEUDOLIFE_LEASES_HELD_PIDS`, which must be a live ancestor of the run (a `lease run` without that record counts while its lock file here is held), and `ops/wsl-suite.ps1` forwards `PSEUDOLIFE_LEASES_HELD` into WSL only for leases whose Windows lock is held. Fail mode gives a board that stops answering one request timeout and one retry, then starts on the local lock, and without a bearer the local lock alone still rules. The recorded run time starts once the board admits the run. `lease hold` is unchanged.
