### Fixed (2026-11-06 — one client update run applies the new release's client steps)
- `pseudolife-mcp update --clients-only`, and the client step of a release-mode `pseudolife-mcp update` (attended, unattended, on a client-only machine, or started by the shim's unattended client update), no longer runs the plugin, Codex hook and tunnel steps with the code of the release it is replacing. Once it has installed and verified the new shim runtime, it hands those steps to that runtime, so behaviour new in the target release runs on the first run instead of a second `--clients-only` (0.17.0's marketplace move to HTTPS ran only on the second). The output names the hand-off ("the client steps after the shim continue in runtime …"). The handed-off run's own ladder, Codex steps, result and exit code are the run's. It never hands off again, and it runs under its parent's update lock.
- A hand-off is skipped at the same version (`--reinstall`) and for a checkout deploy, and it is skipped for a target that predates the hand-off (a downgrade, or a client machine following an older daemon); this run's code then finishes, as before, and says so in one line. A new runtime that cannot start fails the run (exit 5) with the cause and `update --clients-only --tag <version> --reinstall`. The old code never stands in for it.
- Rollout: the hand-off runs in the release being replaced, so it first helps the update *from* the release that ships it. Updating *to* that release still needs a second `pseudolife-mcp update --clients-only` for its own client-step changes. The release-procedure skill's step 6 says which case applies. The native (Rust) updater keeps the two-run shape for now (#1308).
