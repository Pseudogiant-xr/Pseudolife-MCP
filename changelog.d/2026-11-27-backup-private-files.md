### Changed (2026-11-27 — `backup` keeps its dump password and files private to you)
- On Linux and macOS, `pseudolife-mcp backup` with `PSEUDOLIFE_MCP_DATABASE_URL` now hands `pg_dump` the database password through its environment (`PGPASSWORD`) instead of its command line, so other accounts on a shared host no longer see it in the process list. Everything else in the connection string reaches `pg_dump` unchanged. Windows, which shows a command line only to its own account and administrators, passes the string as before.
- There, a connection string that would still need a secret on the command line is refused before `pg_dump` starts, with the fix: an `sslpassword` or `oauth_client_secret` (move it into a `pg_service.conf` entry and name it with `service=`), or a password next to a `service=` or `PGSERVICE`, whose entry's own password would otherwise be used (put the password in that entry). `migrate-flat --apply` reports the same reason.
- Each run writes its dump and state archive to partial files of its own, so two backups started in the same second no longer overwrite each other; on Linux and macOS they are created owner-only (`0600`), and a backup directory the run creates is `0700`. An existing directory keeps the mode you gave it.
