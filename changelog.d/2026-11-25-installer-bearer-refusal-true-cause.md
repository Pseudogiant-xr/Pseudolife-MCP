### Fixed (2026-11-25 — the installers' bearer refusal names fixes that work) [#1968]
- On a host with another release's unfinished Rust daemon container, all four installers now refuse with the container's own refusal (remove the container, then rerun) before the "Rust daemon needs its bearer token" refusal. Before, they named token fixes and an `--engine python` rerun that each led only to that second refusal. A new read-only engine helper step, `foreign` (`ops/installer_engine.py foreign`, and `pseudolife-mcp installer engine foreign` for the native installers), gives that refusal without pulling or writing anything.
- On a host with an accepted Rust daemon and no bearer to come, `--engine python` (`-Engine python`) now gets a refusal that says the switch to the Python daemon needs the token too, because `pseudolife-mcp update` reads the Rust daemon with it first, and that the same rerun makes the switch once the token is set or can be minted. Before, the refusal named only token fixes and said nothing about leaving Rust. `update --engine python --daemon-only` with the bearer gone refuses before changing anything (its refusal names the bearer settings), so it is not offered as a way around it.
- The bash installers' fixes for `--no-token` and `--transport http` now say to rerun with `--transport shim` and without `--no-token`, or to set `PSEUDOLIFE_MCP_TOKEN` in ops/.env and rerun without `--no-token`; setting the token alone does not pass an install run with `--no-token`. The Python-client installers (`ops/install.sh`, `ops/install.ps1`) also name `--no-token` (`-NoToken`) or `--transport http` as the cause when that is why no token can be minted, instead of missing pipx.
