### Changed (2026-10-29 — only integration batches spend hosted CI's heavy lanes)

- An ordinary pull request (any head branch but `integrate/*`) now runs only the fast lanes whatever it changes: `ci.yml`'s `scope`, `guards`, `lock-resolve` and `frontend`, and `rust.yml`'s `Scope`, `Rust`, disposable-image check and `Parity` gate. Until now a pull request editing a workflow, `pyproject.toml`, a lock file or the Rust toolchain pin ran every lane on its own head: on 2026-10-28 such pull requests ran 43 Rust jobs per push, and batch #1031 sat queued for over an hour behind them under the account's 20-job hosted limit. Its batch runs every lane under the edited workflow before the edit can reach master, as the old own-head run did (`docs/dev/merge-batches.md`).
- A newer push to an ordinary pull request cancels that pull request's in-flight runs in both workflows; master pushes, the nightly, manual and stress runs, merge groups and `integrate/*` batch runs each get a concurrency group of their own and are never cancelled, running or pending.
- `python ops/integrate.py` no longer counts a cancelled check on a member's own head as a failure: `build` and `open` admit it like a pending one, and `status` and the batch body show it as `cancelled`. A job GitHub cancelled for running past its `timeout-minutes` (it reports no separate timed-out conclusion) still counts as failing, read from the runner's annotation on the latest attempt of that check; annotations that cannot be read keep the pull request out as `unverified`, and `open` refuses with a retry rather than a drop. A gate job that runs under `always()` (the `Parity / <os>` gate) and failed only because a cancel stopped the jobs it needs also counts as cancelled, read from the workflow at that head and the run's jobs: on 2026-10-30 #1059 was refused as failing although only its `Rust / <os>` jobs had been cancelled. The `Parity / <os>` gate gains a first step, "A needed job was cancelled", that fails exactly when a job it needs was cancelled and skips the verdict step then (the gate's result is unchanged, except that a cancelled `scope` job now fails it while every other needed job passed, which the verdict alone let through). Only a failure at that exact step, with no other job of that run failed, timed out or needing action, counts as cancelled. A gate that failed elsewhere, a head whose gate predates that step, or a needed job unfinished or timed out, still counts as failing. An `unverified` head now names the read that failed. `merge` still refuses a batch whose own check was cancelled or failed.
