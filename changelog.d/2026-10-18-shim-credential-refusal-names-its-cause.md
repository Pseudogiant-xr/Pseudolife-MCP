### Fixed (2026-10-18 — a refused token file says why, and how to fix it)

- When the shim cannot use its token file, the error on every MCP call now names the real reason, the file, and the one fix, instead of "restore the configured credential" for every case. A file that lost its owner-only permissions (a plain rewrite during a token rotation does this) says so and gives the command that restores them: `icacls "<file>" /reset`, then `icacls "<file>" /inheritance:r /grant:r *S-1-3-4:F`, on Windows, `chmod 600 <file>` elsewhere. A file another account owns (one written from an elevated prompt belongs to Administrators) now has its own reason, `credential file is owned by another account`, and its fix is to replace it with a copy the shim's account owns, since narrowing its permissions would lock that account out. A missing file, an unreadable one, a link or junction, a redirected directory and a malformed token each name their own fix. The error's data carries the same `reason`, `recovery` and `credential_file`, and never the token. A token file replaced in the middle of a call now says the credential changed; it says to retry only when the call cannot have reached the daemon, and otherwise keeps the warning to check the call's result first.
- Pseudolife's own token-file writer (used by Codex setup, the Claude Desktop registration and unattended updates) now replaces an existing file you own whose permissions are broader than owner-only, instead of refusing it: the new file is owner-only, so writing it repairs them. Links, hard links, non-files, files another account owns and files whose owner cannot be read are still refused.
