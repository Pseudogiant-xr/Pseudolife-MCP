### Fixed (2026-11-16 — native `doctor` no longer sends tunnel users to the Python client)
- With the native client, `pseudolife-mcp doctor` on a machine with a saved tunnel told the user that three situations needed the Python client. It now names only steps this client runs. A tunnel refresh that needs attention points at `pseudolife-mcp tunnel status --profile <name>`, which now answers beside a process record, or, when that command cannot read the key file or the verification challenge, names that file and asks that it be an owner-only file. A profile the client cannot read says to move it aside if it is left from an abandoned setup, and that this client cannot set a tunnel up yet. An expired key names the date it expired and where to create a new restricted key (`https://platform.openai.com/settings/organization/api-keys`).
- On Windows the saved tunnel key is now unsealed with the account's DPAPI protection, as the Python client sealed it, so `tunnel status` and `doctor` report a protected key as present only after checking it. A key that cannot be unsealed in this session (sealed by another account, damaged, or read over a logon without the account's credentials, such as a key-based SSH logon) is still reported as `not_verified`, and `doctor` says why and to check from a session signed in with the account's password. The unsealed key is wiped from memory after the check and never printed or logged. `tunnel verify` with such a checked key no longer defers: without a running tunnel it refuses, as on other platforms.
