### Fixed (2026-11-24 — an identical client-only installer rerun leaves Codex's token copy registered) [#1908]
- A client-only install with `--token-file X` registers Codex's own copy of X's token. Running the identical command again used to re-point Codex's registration at X itself, so a rerun of a set-up host changed something; a third run then changed nothing. Both native installers (`install-native.sh`, `install-native.ps1`) now treat that rerun's `pseudolife-mcp connect` plan as current when its only changes are Codex's, Codex's registration already names Codex's own copy, the copy holds the same token as X, and Codex's rows would change nothing but that pointer. As for any current plan, they verify the credential against the daemon, apply nothing, and print `Verified the current credential for <clients> at <url>: Codex's registration already names its own copy of the token in <X>. Nothing to write.`, followed by any entries connect cannot rewrite (for example an exported `PSEUDOLIFE_MCP_DAEMON_URL`) for you to change by hand.
- Every other case applies the plan as before. A file that holds a different token (a rotation) moves the registration to X, as do a registration naming another file, a new daemon URL, and any answer the check cannot give. A plan that also changes another client, the environment or a schedule is applied whole.
- A standalone `pseudolife-mcp connect <url> --client codex --token-file X` still selects X, and where Codex's credential is stored is unchanged.
- The check is a new read-only native installer step, `pseudolife-mcp installer codex-token-copy --daemon-url URL --token-file PATH`, with a new `installer connect-report codex-only` mode. It reads Codex's configuration through Codex's app-server, compares the two token files in constant time and never prints a token. Both join installer protocol 5, which no release has shipped yet; an installer that gets no answer from them applies the plan as before.
