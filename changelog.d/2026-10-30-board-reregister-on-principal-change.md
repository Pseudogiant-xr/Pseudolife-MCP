### Fixed (2026-10-30 — a session whose login changed principal gets back on the board)

- A session that saved its board address under one login, and was then moved to another principal on the same bank (for example by pairing the machine with `pseudolife-mcp invite` and `connect --read-code`, which repoints its clients at a per-machine token), was refused at every start: the saved address no longer matched the login, so the shim ran memory-only and every `memory_agents` update and `memory_message` was refused with `instance_authentication_required`. A restart read the same file. The Python and Rust shims now set that address aside with a `.stale` suffix, print one line saying the saved address belongs to another login on this bank, and register a fresh address under the current login, as a new session would; the old address's key is never sent. A saved address bound to a different bank is still kept and refused, unversioned state still has to prove itself to the bank before it is upgraded, and a running session whose login changes still stops background delivery until the login is restored. When the shims do refuse a saved address at startup, the "coordination unavailable" line now names that cause (an address bound to another bank, or one the bank did not prove) and the fix (point the client back at that bank, or move the file aside and restart), instead of the generic checklist.
