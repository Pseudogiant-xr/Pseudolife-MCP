### Changed (2026-11-16 — the product no longer tells users to run things as root)
- A Tailscale serve refused for this user (`maintainer setup`) names only the least-privilege fix: on Linux, make the user Tailscale's operator once (`sudo tailscale set --operator=$USER`); on Windows, run it as the account that owns the device's Tailscale configuration. It no longer suggests running as root or from an elevated shell, which forwarding a port never needs.
- The Docker-group advice in the README and the preflight (`ops/preflight.sh`, `ops/preflight-native.sh`) now says plainly that membership of the `docker` group is equivalent to root on that machine, that this is how Docker works rather than something Pseudolife adds, and that running the installer from an account that already uses Docker avoids granting it. Rootless Docker and Podman are not supported yet (#1642).
- A client config file another account owns (often one a `sudo` run created) is refused with the narrowest fix: a copy this user owns (`mktemp`, `cp`, then `mv -f`) when it can write the folder, `chmod u+wx` on the folder first when it owns but cannot write it, and only otherwise a `sudo chown` for an administrator to run, which names this account rather than `$USER` (of the file alone in a shared sticky folder, of the folder and the file elsewhere). A run as root is told to run again as the file's owner, without sudo.
- The Windows access-list repairs for private state folders say when an elevated prompt is needed and why: only for a folder owned by Administrators (as one an elevated process created is); a folder SYSTEM owns must first be taken over by an administrator.
- The `move --to` example target is `user@box` instead of `root@box`, in the help, the usage refusal and the guide.
