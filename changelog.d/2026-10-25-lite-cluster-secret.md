### Security (2026-10-25 — lite banks get their own superuser password instead of postgres/postgres)
- The lite tier's embedded PostgreSQL used the fixed superuser password `postgres` with cleartext password authentication on loopback, so any process on the machine, under any account, could open and change the bank. Each bank now has a random 64-hex-character password in `<data_dir>/embedded_pg.secret`, written owner-only (an explicit owner-only ACL on Windows, mode 0600 elsewhere), and the server authenticates with `scram-sha-256`. The password is never passed to pg0, so it appears on no command line and in none of pg0's files. `pseudolife-mcp backup` hands it to `pg_dump` through `PGPASSWORD`.
- An existing bank moves over at its next start by the daemon or a lite CLI command, with nothing to do by hand. The move survives an interruption at any step, including a killed starter that left the server running: `pg_hba.conf` records the progress and the next start finishes it. A missing secret file gets a new password the same way. A new bank briefly keeps pg0's default password between initdb and its first move, and only on its first start.
- No going back to an older release: once a bank has moved, a Pseudolife release from before this one cannot start it, and cannot attach to it. Upgrade every runtime that opens the bank (daemon, shims and CLI) together.
- `pseudolife-mcp backup` leaves `embedded_pg.secret` out of its state archive: a restore loads the dump into a fresh cluster with its own password, and an old one extracted over it would lock the bank.
- Decided by the maintainer on 2026-10-25 for the Rust port's lite tier (decision 8 in `rust/daemon/spec-lite-storage.md`); this Python fix lands first so both daemons use one credential.
