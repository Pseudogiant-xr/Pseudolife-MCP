### Added (2026-11-16 — the native client has its own tunnel bridge)
- `pseudolife-mcp tunnel shim`, a hidden command, is the MCP server OpenAI's `tunnel-client` starts for a tunnel. It runs this runtime's own stdio shim as a child, pointed at the profile's daemon and token file, and relays its messages unchanged. The child never inherits a token (`PSEUDOLIFE_MCP_TOKEN*`), a daemon address or `OPENAI_API_KEY` from the bridge's environment, starts no daemon, and opens no window on Windows. Nothing starts the bridge yet: the native `tunnel run` that launches it comes in a later change.
- A successful `memory_search` call whose query carries the profile's pending verification nonce, or a `memory_agents` `list` call whose project does, writes a payload-free receipt beside the challenge (`<profile>-verification/<nonce>-<tool>.json`, owner-only). The receipt is written after the answer has been relayed, so the session never waits for it. A failed call, a call without the nonce, a wrong nonce, another profile's nonce, or a profile changed since the bridge started writes nothing. If a receipt cannot be saved, the bridge says so once on stderr and the session continues.
- With `minimum_catalog: full`, each `tools/list` waits until `memory_toolset` reports the full tier, expanding it at most twice. A tier that stays short, or no answer within 15 seconds, refuses that listing with one error. With the default catalog, listings pass through unchanged.
- The bridge relays each direction through its own bounded queue, so neither side can stall the other or grow its memory without limit. When the client leaves, the shim's input closes and it gets five seconds to finish. The bridge ends within 30 seconds of the client leaving, and a shim that takes none of its waiting input for a minute is treated as hung, which also ends the session.
- Started by hand, or without `--profile`, `tunnel shim` refuses with one line naming what it needs, before it reads anything or starts the shim. It also refuses a profile that is not ready.
