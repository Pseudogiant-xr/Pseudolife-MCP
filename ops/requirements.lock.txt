# torch is pinned to the CPU build and MUST stay that way (2026-07-29). The
# daemon is a CPU-only service — the image sets CUDA_VISIBLE_DEVICES=-1 and
# there is no GPU code path — but PyPI's linux torch wheel is the CUDA build,
# which drags in ~4 GB of nvidia-*/cuda-*/triton wheels. The '+cpu' local
# version only exists on PyTorch's own index, which ops/Dockerfile.daemon
# installs from BEFORE applying this file as a constraint; the pin here is
# what stops pip re-resolving torch out from under that install.
#
#   *** setuptools and torch are COUPLED. Bump them together or not at all. ***
#
# 2026-08-02: torch 2.12.0+cpu -> 2.13.0+cpu and setuptools 78.1.1 -> 83.0.0
# bumped TOGETHER for Dependabot alerts #6/#7 (setuptools MANIFEST.in
# exclusion bypass; torch.jit.script memory corruption). torch 2.13.0 has
# no setuptools ceiling, so the 78.1.1 hold below is history, kept for the
# lesson. Dockerfile.daemon's pre-install pin bumped in the same change;
# tests/test_daemon_image_is_cpu_only.py still guards the CUDA-pull trap.
#
# torch 2.12.0 requires setuptools<82. A Dependabot bump to setuptools==83.0.0
# (17b97180, 2026-07-24) crossed that ceiling, and because a constraint file
# cannot be negotiated, pip resolved the conflict by discarding the pinned CPU
# torch and walking forward to 2.13.0 (no setuptools ceiling) — silently
# shipping the CUDA build in every image built between then and 2026-07-29.
# Nothing in the dependency graph requires torch > 2.12.0; the pull was a
# ceiling collision, not a raised floor. tests/test_daemon_image_is_cpu_only.py
# now fails on exactly this, so a future bump cannot land the same way.
#
# Security holds (Dependabot triage, 2026-07-16) — carry these notes forward
# when regenerating this file from pip freeze:
# - chromadb 1.5.9 is the latest release; CVE-2026-45829 (critical, pre-auth
#   code injection) has NO patched version yet. The vulnerable code is the
#   Chroma HTTP server API — the daemon only embeds chromadb.PersistentClient
#   and never runs that server, so the path is unreachable. Bump the moment a
#   patched release exists.
#   2026-08-27: three more server-side chromadb CVEs, same verdict, still no
#   patched release (1.5.9 remains latest): CVE-2026-45833 (critical,
#   authenticated RCE via trust_remote_code on the collection-update
#   endpoint), CVE-2026-45830 (cross-tenant read/write for any authenticated
#   user), CVE-2026-45831 (SimpleRBACAuthorizationProvider ignores
#   tenant/database/collection scope). All three live in the Chroma HTTP
#   server and its auth providers; the daemon's only chromadb use is the
#   embedded PersistentClient in pseudolife_memory/memory/reference_bank.py
#   (no HttpClient, no server, no auth providers anywhere in the tree), so
#   none of the paths exist at runtime. Re-check on the next chromadb release.
# - transformers is held at 4.57.6 (the last 4.x release): the fixes for
#   CVE-2026-1839 / CVE-2026-4372 / CVE-2026-5241 are 5.x-only, but
#   optimum-onnx (the ONNX embedding backend the image ships as its default)
#   caps transformers<4.58. All three CVEs require loading attacker-controlled
#   models/checkpoints; the image runs HF_HUB_OFFLINE=1 with pinned baked
#   weights, so they are unreachable at runtime. Bump to >=5.5 as soon as
#   optimum-onnx supports transformers 5.x.
